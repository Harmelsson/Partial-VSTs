## The Vision (Long-Term, Keep In Mind While Building Anything)

This is not "a calculator app." The calculator is the *first module* of something intended to grow, over years, into:

- A standalone application — **not a browser app, not a VST/plugin**. A DAW-like environment, but built to *find sounds*, not to produce finished commercial music.
- Multiple synths/"note modulators" living inside one shared environment, increasing in sophistication over time — the first ones simple, later ones capable of much more.
- Custom effects (EQ, etc.) that can read a synth's harmonic/tuning data directly — e.g., an EQ point that jumps to the frequency of a note's fundamental automatically.
- A shared harmonic/tuning data model: partials, scale degree, base/stretch number, etc., that any module (synth or FX) can read from, live, without needing to hand-craft or exchange .scl/.kbm/.tun/.fnv files.
- Real-time partial stretching, consonance/dissonance generators, and other tools "the limits are truly endless" on, per the user's own words.
- Custom MIDI receivers that can dynamically reflect an arbitrary N-note scale (e.g. 32 notes/octave) on a visual digital MIDI player/keyboard, without manual remapping hassle.
- A core interaction philosophy: **everything should be finely, continuously scrubbable by mouse** — not "type number, hit enter, see result" but "drag and feel the sound shift in real time," including per-digit precision control (see UI section below).
- A modular, patchable mental model even at small scale: calculated values (e.g. partials) should be treated as a *default/generated* layer that manual overrides can sit on top of — "everything can affect everything else," Serum/Phaseplant/Bitwig-modular style, added incrementally over time.

**Explicit non-goals:** no browser deployment, no VST/AU plugin hosting or format compliance, no goal of producing "finished songs" as the software's purpose.

**The realistic scope assessment (for context, not to dampen ambition):** deliberately engineered inharmonic/xenharmonic sound design is a real ~50-year-old field (Sethares' dissonance-curve work, 1970s spectral music, even a hyperpiano — a physical instrument built around engineered partials). What's rare — possibly novel — is *this specific interaction model*: a live, continuously-scrubbable interface where a shared harmonic data model drives multiple synth/FX modules in real time, rather than a scale calculated once and baked into a static tuning file. That's the actual target, not "invent xenharmonic music."

## Core Mathematical Foundations (What the Software Needs to Model)

This is the working math the software's first modules are built to compute. It comes from prior hands-on exploration work (done by hand/by calculation before any software existed) — the software's job is to make this live and scrubbable instead of manually calculated per-session.

### The Harmonic Series & Partials
- Any 1D vibrating object naturally produces integer multiples of its fundamental (2x, 3x, 4x...) — these are **harmonics**.
- **Partials** is the general term — harmonics are partials at exact integer positions; **inharmonic partials** sit at non-integer positions (bells, gongs, or synthetically designed spectra).
- This software's core premise: partials do not have to be integer multiples. They can be deliberately, precisely designed.

### Why Pitch Is Logarithmic
- Musical intervals are ratios, not fixed Hz differences — an octave is always a 2:1 frequency ratio regardless of register.
- Cents are the standard unit: 1200 cents = one octave, always, on any base.

### Timbre-Scale Coherence — the Sethares Principle (Core Design Philosophy)
- Consonance is relative to a sound's own partial structure (timbre), not an absolute property of a scale.
- Source: William Sethares, *Tuning, Timbre, Spectrum, Scale* — the scale that sounds "correct"/consonant for a given timbre depends mathematically on that timbre's own partials.
- **This is the foundational design idea the whole software project is built around**: design a partial/timbre structure and a scale together, from the same underlying math, rather than treating tuning and timbre as unrelated systems (which is how most existing tools — Harmor, Surge, Phase Plant — treat them; see prior exploration work for confirmed tool limitations).

### The "Base Number" / Stretched Harmonics Method (Current Working Engine)
This is the specific technique the v1 calculator formalizes:
- Take integer harmonics (1, 2, 3, 4...) and apply a stretch so the perceived "octave" lands wherever you choose, rather than always at exactly 2:1.
- **Stretch factor = log₂(base number)**. Partial *n*'s frequency ratio to the fundamental = n^(stretch factor).
- Example: base number 2.5 → stretch factor ≈ 1.32193 → partial 2's ratio is 2^1.32193 ≈ 2.5 (i.e., the "octave-equivalent" is 1586 cents instead of the normal 1200 cents).
- Internally consistent by construction: the timbre's partial spacing and the scale's "octave" are generated by the same number, so they're guaranteed to relate mathematically rather than being arbitrarily paired.
- Different base numbers produce different amounts of "richness" (distinct notes findable per octave-equivalent) — prior exploration scanned bases roughly 1.9–3.5 and found richness varies non-linearly (e.g. base 2.5 → 10 notes, base 3.5 → 12 notes, using a specific dissonance-curve method described below).
- **Known dead end, useful as a design lesson:** using the golden ratio φ as the base produces perfectly *evenly*-spaced partials in cents, which yields no usable scale structure — richness requires *uneven* partial spacing/crowding. Any future "generator" module that produces perfectly even spacing will hit this same problem; worth guarding against or at least flagging in the UI if it comes up.

### Two Distinct Kinds of Consonance (Both Need To Be Computable — Different Math)
This distinction matters architecturally: these are two separate algorithms, not one, and a future "consonance/dissonance generator" module needs to support both.

**1. Self-consonance / dissonance curve (single tone, melodic use)**
- Finds which notes minimize beating *within a single tone's own partial series* played against itself at an interval.
- This is the classic Sethares "dissonance curve" approach: plot dissonance score against interval size for a given partial structure, find the local minima — those are the consonant scale-degree candidates for melodic/solo use.

**2. Cross-note harmonic coherence (multiple simultaneous notes, chords/harmony)**
- A genuinely different question: given two notes at frequency ratio R, do their partial series overlap near simple integer ratios *with each other* (not just internally)?
- Method: for stretch factor S, note B's partials sit at R × n^S relative to note A's fundamental. Consonance condition: R × n^S ≈ m^S for small integers m, n. Solving for R gives candidate scale-note ratios: **R ≈ (m/n)^S**.
- Implementation approach used so far (by hand, pre-software): scan integer pairs (m, n) up to some bound (e.g. 28), compute (m/n)^S in cents, cluster nearby candidates, score all pairs/triads/quads by how many cross-partial intervals land near consonant simple ratios within some cents tolerance, using some number of partials per note (e.g. 16).
- This is the method that produced the current best result: a 6-note harmonically-optimized scale for base 2.5 (0, 157.9, 382.3, 537.8, 658.4, 816.3, 1586.3 cents) where all 15 pairs of notes have a consonant cross-partial relationship. Concrete proof the method works, worth keeping as a regression-test case when the software implements this calculation.

### Alternative Partial-Generation Rules (Future "Swappable Generator" Candidates)
The stretch formula (n^S) is meant to be just *one* pluggable way to generate a partial series — not the only one. Known candidates already discussed, for whenever the generator-swapping architecture is built:
- **Arithmetic partial series**: instead of geometric stretching, use arithmetic spacing — fundamental F, "magic number" M, series = F, M×F, (2M-1)×F, (3M-1)×F... Gaps in Hz stay constant while ratios keep shrinking going up; produces no repeating interval at all (every register sounds different). Real-world analog: bells, metallophones, drum membranes. Hypothesized to feel more tribal/percussive/bell-like than stretched harmonics.
- **Voice-derived partials (FFT-extracted)**: record a real sound (e.g. a sustained vowel), run FFT to extract its actual partial fingerprint/amplitudes, use that as a custom partial structure. Not yet implemented anywhere, including by hand — a "future ideas" item, not a validated method like the two above.
- **Cross-note partial optimization (most ambitious, unvalidated)**: instead of picking a generation rule and deriving a scale from it, work backwards — define a target consonance goal across a whole scale, then solve for *both* timbre (partial positions) and scale simultaneously via optimization (e.g. gradient descent or genetic algorithm over partial positions as free variables), potentially allowing different note-pairs to be consonant via completely different partial relationships (no single rule governing the whole system). Explicitly unimplemented and unvalidated — flagged as real and worth pursuing eventually, not a near-term build target.

### Terminology Note
- **Xenharmonic** (not "microtonal") is the correct term for this project's territory — microtonal implies 12-EDO as a baseline with extra notes added; xenharmonic means operating in a fundamentally different harmonic universe (term coined by Ivor Darreg, 1970s). Worth using consistently in code comments/UI copy if it ever needs user-facing terminology.

## Technology Decision — Rust (Decided, Do Not Relitigate Without New Info)

### Why Rust, and why not the alternatives considered:
- **Not React/JavaScript/browser**: was the original (wrong) suggestion early in this project's discussion, based on a false assumption that this was headed toward a browser-based tool. It is not. Real-time audio in-browser is a second-class citizen and was never actually what the user wanted — this was a scoping misunderstanding on the agent's part, corrected once the full vision was described.
- **Not JUCE/C++ for plugin hosting**: unnecessary weight, since this will never be a VST/AU. JUCE-the-framework was considered but its plugin-format machinery is dead weight for a standalone-only app.
- **Not Python** (sounddevice/pyo/RtMidi): fastest to prototype, but poor real-time performance ceiling for low-latency polyphony and custom per-voice DSP — wrong permanent foundation.
- **Not SuperCollider**: a genuinely strong alternative for exactly this kind of research (arbitrary tunings, live synthesis experimentation, 25-year lineage of xenharmonic/spectral composers using it) — flagged as the best "hear sound fastest" option. Not chosen because the user explicitly prioritized long-term code quality/limitlessness over fastest-to-first-sound, given that the user isn't the one coding and wants a foundation worth a decade of investment.
- **Rust chosen because:** best balance of long-term code quality, safety (fewer runtime surprises — important since the user debugs by ear, not by reading errors/stack traces), and being unconstrained by legacy plugin-format cruft. Likely libraries: `cpal` (audio I/O), `midir` (MIDI I/O) — not yet implemented/verified in code, just the current expectation.

### Working relationship model:
- Agent writes 100% of the code.
- User runs it, listens, and reports symptoms in plain language ("the attack is too clicky," "note 4 sounds wrong vs note 3," "I want a knob that does X").
- Agent translates feedback into code changes.
- Because the user can't self-verify code correctness by reading it, architecture must stay simple enough that bugs don't hide silently for long stretches.

## V1 Spec — "Modulator #0": Fundamental + Stretch Calculator

This is the deliberately tiny first step. Scope is intentionally narrow; the ideas above (override layers, multiple modulators, shared data model) are to be *kept in mind architecturally* but NOT built yet.

### Inputs
- **Fundamental frequency** — default 440 (Hz). Live-updating, no delay, no enter-to-confirm.
- **Stretch factor ("X")** — default 2 (the normal octave/integer case). Live-updating same as above. Manually enter decimals.

### Output
- A live-updating list of partials, each showing its calculated stretched frequency.
- Formula: partial *n*'s frequency ratio to the fundamental = n^(log₂(base number)) — i.e. this calculator is the general-purpose, live-scrubbable engine version of the "base number" stretched-harmonics method described in Core Mathematical Foundations above, which was previously only calculated by hand per-session.

### Explicitly OUT of scope for v1 (documented so future-agent doesn't assume it exists):
- No manual override layer (grabbing a partial and nudging it off its calculated position) — planned for v1.1+.
- No swappable "generator" formulas (arithmetic spacing, manual partial entry, etc.) — planned for later; the stretch formula is meant to be just *one* pluggable way to generate partials, not the permanent/only way.
- No GUI polish beyond the core interaction (see UI section) — sequencing question below still needs an answer.
- No second modulator, no FX, no MIDI mapping, no shared cross-module data model yet — all noted as future direction, not v1 work.

## UI/Interaction Design Notes (For When GUI Work Begins)

### Per-digit scrubbing ("Harmor pitch-articulator style")
- Each digit of a displayed number (including decimal places) should be individually mouse-draggable — dragging the tens digit changes the value by 10s, dragging the 4th decimal place changes it by 0.0001s, etc.
- User should be able to toggle how many decimal columns are visible (e.g. show 3 vs show 12) without changing the underlying stored precision.
- This should be treated as a reusable UI component/pattern for the whole app going forward, not a one-off for this calculator — future modulators, FX, etc. should reuse the same interaction.

### Precision: display vs internal storage (agreed distinction)
- **Internal storage:** full 64-bit float precision (effectively arbitrary for this project's purposes) — never round for storage.
- **Display:** default to a reasonable number of decimals (discussed ballpark: ~4), but this is a *view setting*, not a data-truncation. The per-digit scrubbing UI above is what actually exposes/hides precision to the user, not a fixed display format.
- Rationale: fine mouse-scrubbing at very small deltas (well beyond 4 decimals) can be audibly relevant at higher partials in a stretched harmonic series — truncating early would silently remove real sonic exploration range.
- Drag sensitivity should likely support a coarse mode (normal drag) and a fine mode (e.g. modifier key or separate fine-tune interaction) rather than one fixed sensitivity — not fully speced yet, just flagged as needed.

### The "copy-paste live data" mental model (important future constraint, not a v1 task)
- User's mental model for how synths will eventually consume note data: a note's properties get "copied," then "dynamically pasted" inside a synth module, and the synth operates directly from those live numbers.
- Practical implication for later architecture (not now): whatever data structure a "note" becomes must be designed so it can be handed to a synth module and scrubbed *from either side* — i.e., changing a global setting related to a note should propagate seamlessly and be feelable in real time via mouse, not require a re-trigger or explicit reload step.
- Do not design this shared data model yet (explicitly deferred by the user) — just don't build v1 in a way that would make this awkward later (e.g., avoid baking assumptions that partials are always exactly formula-derived with no possible override, since the override layer is coming).

## Longer-Term Architecture Intentions (Not Yet Designed, Just Flagged)

- **Modular "note" data model**: eventually needs to carry at minimum fundamental frequency, partial series (positions + amplitudes), scale degree, and the base/stretch number that generated it — flagged by the agent as the highest-value/hardest-to-change design decision, but explicitly NOT to be designed until the user is ready (user was clear: "don't design that part now for sure, I just want a calculator first").
- **Generator vs. override layering**: partials (and likely other properties) should eventually be split into (1) a generator/rule that proposes a value, and (2) an override layer of manual adjustments that persist independent of the generator's inputs. This is meant to generalize beyond just partials — "layers on top of technically any information a note has," per the user.
- **Multiple modulators (synths) in one environment**, each more capable than the last, all sharing the same underlying data model so they can be combined/patched together later (Serum/Phaseplant/Bitwig-modular-style "everything connects to everything," at the project's full maturity — not v1).
- **Project code structure** should be scaffolded from the start (once building begins) so that "modules" are a real concept in the code even when only one exists — the goal is that adding modulator #1, or the override layer, is additive later rather than requiring a rewrite of modulator #0's foundations. Concrete structure not yet decided — to be figured out when implementation actually starts.
- **Documentation habit to maintain going forward**: keep a running architecture doc alongside the code itself (separate from this session-notes file) once a real codebase exists, explaining module layout, the shared data model, and current state — so a future agent session can onboard from the repo itself, not just from this notes file.
